# μLearn Flutter App — Project Rules

This file is the standing reference for anyone (human or AI agent) working on this codebase. If you're an AI coding assistant, treat this as binding unless the person explicitly overrides a specific rule for a specific task. When a request conflicts with this file, follow the request but flag the conflict rather than silently deviating.

---

## 1. Stack (do not substitute without discussion)

| Layer | Choice | Notes |
|---|---|---|
| State management | Riverpod 3.0, code-gen (`@riverpod`) | Never introduce Provider, GetX, Bloc, or manual `StateNotifierProvider` in new code. |
| Routing | go_router | `redirect` reads auth state from a Riverpod provider — never do manual `Navigator.push` for top-level auth flows. |
| Env config | envied | Never add `flutter_dotenv` or read `.env` files at runtime. |
| Networking | Dio | Generated client (see §4) for standard CRUD; hand-written Retrofit interfaces only for non-standard endpoints. |
| Models | Freezed + json_serializable | All domain entities and DTOs. No hand-written `copyWith`/`==`/`toJson`. |
| Backend | Django REST Framework + SimpleJWT + drf-spectacular | Response envelope and auth patterns are backend-defined — see §3. |
| Local cache | dio_cache_interceptor (Hive store) | HTTP response caching only. No offline-first datastore (Isar/Drift) unless a specific feature explicitly requires true offline capability — that's a per-feature decision, not a blanket one. |
| Secure storage | flutter_secure_storage | Tokens only. Never put tokens in `SharedPreferences`. |
| Lints | very_good_analysis (or flutter_lints, strict) | `flutter analyze` must pass with zero warnings before a PR is opened. |

## 2. Architecture — feature-first Clean Architecture

```
lib/
├── core/           # shared across all features — features never import each other directly
└── features/
    └── <feature>/
        ├── data/           # DTOs, remote/local datasources, repository implementations
        ├── domain/         # pure Dart entities, abstract repository contracts, use cases
        └── presentation/   # Riverpod controllers, screens, feature-local widgets
```

**Hard rules:**
- `core/` never imports from `features/`.
- `features/X` never imports directly from `features/Y`. Shared logic goes in `core/` or gets promoted to a shared package. If you find yourself needing this, stop and flag it — don't just add the import.
- `domain/` has zero Flutter imports and zero Dio/HTTP imports. It's pure Dart. If a domain file needs `package:flutter/...` or `package:dio/...`, that logic belongs in `data/` or `presentation/`, not `domain/`.
- Repository *contracts* (abstract classes) live in `domain/repositories/`. Repository *implementations* live in `data/repositories/`. Presentation layer depends on the abstract contract, never the concrete implementation, via Riverpod DI.
- DTOs (raw API shape) and domain entities are **separate classes**, connected by a `toDomain()` mapper on the DTO. Never let a DTO leak into `presentation/`. This is what protects the UI when the backend renames a field — you fix one mapper, not every screen.
- Screens are dumb. They call `ref.watch(someControllerProvider)`, get an `AsyncValue`, and render `.when(data:, error:, loading:)`. Business logic does not live in widgets.

## 3. Backend integration rules

- **Response envelope:** every DRF endpoint returns `{ hasError, statusCode, message, response }`. The actual payload is always under `response`. DTOs should model `response`'s contents directly — don't make every DTO re-model the envelope; handle envelope unwrapping once, centrally, in the Dio response interceptor or a shared parsing helper.
- **Error shape:** DRF validation errors are field-keyed (`{"email": ["This field is required."]}`), not a single message string. The shared `ApiException` parser must handle this shape. Never assume errors are a flat string.
- **Auth:** SimpleJWT, access + refresh token pair. The interceptor in `core/network/auth_interceptor.dart` attaches `Authorization: Bearer <token>`, catches 401s, attempts one silent refresh, retries the original request once, and on unrecoverable failure clears secure storage and flips the auth controller to signed-out — which the router `redirect` picks up automatically. Never manually navigate to sign-in from inside a repository or interceptor.
- **Spec is not always literal.** The OpenAPI schema is generated by drf-spectacular and can mistype `SerializerMethodField`s (e.g. a field that's actually a list typed as `string` in the spec). **Before writing a DTO for a field whose type looks suspicious, verify against a real API response.** Don't build UI or parsing logic around an unconfirmed guess — flag it and ask, or hit the dev backend directly.
- **Client generation:** prefer generating the Dio client from the live schema (`/api/schema/`) over hand-writing Retrofit interfaces, for CRUD-heavy resources. Treat generated code as a build artifact — regenerate on schema changes, don't hand-edit it. Hand-written Retrofit is fine for the handful of endpoints with non-standard shapes.
- **Caching:** the cache interceptor sits *before* the auth interceptor in the Dio chain, so cache hits skip token logic. TTL policy is per-endpoint, not global — see the architecture doc for the leaderboard/course-content/profile examples. Any mutation that changes cached data must explicitly bust the relevant cache key(s) in the repository layer, right after a successful write — this is the repository's job, not the controller's.

## 4. Riverpod conventions

- Use `@riverpod` code-gen annotations exclusively. No manual `Provider((ref) => ...)` boilerplate in new code.
- Controllers extend `_$ControllerName` and expose `AsyncNotifier<T>` for anything async. Use `AsyncValue.guard()` for mutations so loading/error states are automatic.
- Screens never call repositories directly — always through a controller. This is what makes state testable via `ProviderContainer` overrides without touching widgets.
- Keep providers scoped to the feature that owns them (`presentation/providers/`) unless genuinely cross-feature (then it goes in `core/`).
- Prefer last-good-state-visible-during-refresh over full-screen loading spinners on refetch, where the UX benefits (e.g. pull-to-refresh on a list). Don't reflexively use `AsyncLoading` for every refetch.

## 5. Naming & file conventions

- File names: `snake_case.dart`. Class names: `PascalCase`. One public class per file, matching the filename (e.g. `AuthController` in `auth_controller.dart`).
- DTOs suffixed `Dto` (`UserProfileDto`), domain entities unsuffixed (`UserProfile`), repository contracts suffixed `Repository` (`ProfileRepository`), implementations suffixed `RepositoryImpl` (`ProfileRepositoryImpl`).
- Riverpod providers/controllers suffixed `Controller` for stateful async notifiers, `Provider` for simple derived/computed values.
- Route paths centralized in `core/router/route_paths.dart` as constants — never hardcode a route string inline in a widget.

## 6. Testing

- **Domain/use cases:** pure unit tests, no mocks needed since repository contracts are interfaces.
- **Controllers:** `ProviderContainer(overrides: [...])` + `mocktail` for repository mocks. No codegen mocking library.
- **Widgets:** `flutter_test`; reach for `patrol` only if a test genuinely needs real device interaction (deep links, permissions) beyond `WidgetTester`.
- **Golden tests:** for brand-critical screens where a visual regression matters (not required for every screen).
- New features need at least controller-level test coverage before merge. UI-only changes (copy, spacing) don't need new tests but shouldn't break existing ones.

## 7. Git & PR discipline

- Conventional commit style: `feat(auth): add sign-in screen`, `fix(profile): handle null profile_pic`, `refactor(network): extract cache key builder`.
- Generated files (`.g.dart`, `.freezed.dart`): commit them. This project prioritizes low-friction onboarding for a mostly-volunteer contributor base over strict "generated files are build artifacts" purity — don't fight this convention without discussing it first.
- `flutter analyze` and `flutter test` must pass locally before opening a PR. Don't rely on CI to catch what a 30-second local check would have caught.
- No commented-out code blocks left in a PR. Delete it — git history has it if it's needed again.
- No `print()` statements in committed code. Use a proper logger (decide on one — e.g. `logger` package — and use it consistently once chosen).

## 8. Design & theming

- Brand tokens live in `core/theme/mulearn_colors.dart` and `core/theme/mulearn_theme.dart` — this is the single source of truth, ported from the landing page's CSS custom properties. Never hardcode a hex color inline in a widget; reference `MulearnColors.primary` etc.
- Primary blue `#0961F5`; brand gradient 135° `#2E85FE → #AF2EE6`; supporting neutrals greyish `#C4C4C4`, blackish `#1A1A1A`, whitish `#FEFEFE`, gray-600 `#666771`.
- Match heading weight hierarchy from the web app (h1 heaviest/black down to h5 medium) rather than inventing a new scale.

---

## 9. Scope discipline

- Build only what's asked. If a task looks like it needs a related feature "while we're in there," stop and flag it rather than expanding scope unasked — this applies to both AI agents and human contributors reviewing AI-generated PRs.
- Don't add a dependency not already in this file without discussing it first. If a task seems to need one, name the specific gap and propose the addition rather than silently pulling in a package.
- When the OpenAPI spec is ambiguous or looks auto-generated-and-wrong for a field you're about to build against, verify against a real response before writing code around a guess (see §3). This is the single most common way bugs get introduced in this codebase — don't skip it to save time.

---

## 10. When this file and a request conflict

Follow the person's explicit request for the task at hand, but say so — e.g. "this uses Provider instead of Riverpod per your request, which is a deviation from rules.md §1; flagging in case that wasn't intentional." Silent deviation is the failure mode this file exists to prevent.
